# レビュー観点ガイドライン

## 1. コード品質

### 命名規則
- 変数、関数、クラス名の一貫性
- 意図が明確に伝わる命名
- プロジェクトの命名規約への準拠

### 単一責任原則
- 関数/メソッドが単一の責任を持つか
- 適切な粒度での責任分割

### DRY原則
- コードの重複が排除されているか
- 共通処理が適切に抽出されているか

### エラーハンドリング
- 適切な例外処理
- エラーメッセージの明確性
- リソースの適切なクリーンアップ

## 2. セキュリティ

### 入力検証
- ユーザー入力の適切な検証・サニタイゼーション
- 型チェックと境界値チェック

### 機密情報
- ハードコードされた認証情報がないか
- 環境変数・シークレット管理サービスの活用

### 認証・認可
- 適切な認証チェックとアクセス制御
- セッション管理・トークン検証

### 脆弱性対策
- SQLインジェクション、XSS、CSRF対策
- OWASPトップ10への対策
- 依存ライブラリの脆弱性チェック

## 3. パフォーマンス

### アルゴリズム効率
- 適切な時間計算量（O(n), O(log n)等）
- 効率的なデータ構造の選択

### 不要な処理
- 無駄なループや再計算の排除
- キャッシュ可能な値の再利用

### メモリ使用
- メモリリークの有無
- 大量データの適切な処理（ストリーミング等）

### N+1問題
- データベースクエリの最適化
- バッチ処理・適切なJOIN・インデックス活用

## 4. テスト

### テストカバレッジ
- 変更に対する適切なテスト
- 重要な機能のテスト網羅

### エッジケース
- 境界値・エラーケース・異常系のテスト

### テスト可読性
- テストケース名の明確性
- Given-When-Then構造の活用
- テストの独立性

## 5. 設計

### 既存パターン
- プロジェクトの既存パターンとの一貫性
- コーディング規約への準拠

### 拡張性
- 将来の変更への対応しやすさ
- Open/Closed原則の適用

### 依存関係
- 循環依存の回避
- 依存性注入の活用

### インターフェース
- API設計の適切さ（RESTful原則）
- レスポンス形式の一貫性
