# 振り返り・ゲート判定チェックリスト

> **context-manager が利用できない場合**: チェックリスト中の context-manager 関連項目（知見保存・候補検討）はスキップする。保存すべき知見は SESSION-NNN.md §4 または plan.md 末尾の振り返り欄に記載する。
>
> **小規模プラン（3-5タスク）**: 層1 のみ適用。層2（フェーズゲート判定）は不要。

## 層1: セッション振り返り（毎セッション終了時）

### 実行結果の確認

- [ ] 完了したタスクは plan.md の完了条件を満たしているか？
- [ ] 未完了のタスクがある場合、中断理由は明確か？
- [ ] テストは実行したか？結果はどうだったか？

### 発見と学び（判断を要する問い）

- 今回のセッションで、プラン作成時には想定していなかった事実が判明したか？それはプランの前提に影響するか？
- 実装中に選択した設計方針は、プランに記載された方針と一致しているか？乖離がある場合、それは改善か逸脱か？
- context-manager に保存すべき知見はあるか？（判断基準: 将来の別セッションで役立つか）。context-manager 不在時はセッション記録に記載

> **形骸化防止**: 「問題なし」の場合も、なぜ問題ないかを1行で記録する。context-manager が利用可能な場合は毎回必ず保存候補を1つ以上挙げる（保存しない判断もOKだが、候補は出す）。

### 次セッションへの準備

- [ ] 次セッションの実行者が、このセッションの続きを迷わず始められるだけの情報を引き継ぎに記載したか？
- [ ] ブロッカーがある場合、その解消方法または回避策は明確か？

## 層2: フェーズゲート判定（フェーズ完了時に追加）

層1 の全項目に加えて、以下を実施する。

### フェーズ目標の達成度

- フェーズの目標（plan.md に記載）は達成されたか？
- 達成されていない場合、残作業を次フェーズに持ち越すか、現フェーズで完了させるか？

### 前提条件の検証

- 次フェーズの前提条件は、現在も有効か？
- 現フェーズの実装結果が、次フェーズの設計に影響を与える変更を含んでいないか？

### 軌道修正の要否判定

以下のいずれかに該当する場合、**plan-creating に修正を委譲**する:

- [ ] プランの前提条件が崩れた
- [ ] 次フェーズのタスク設計が現実と乖離している
- [ ] 新たなリスクが発見され、リスク対策の追加が必要
- [ ] スコープの変更が必要

該当しない場合は、その理由を1行で記録して次フェーズに進む。
