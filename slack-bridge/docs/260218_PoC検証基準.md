# slack-bridge PoC 検証基準書

作成日: 2026年02月18日

## 1. 目的

slack-bridge の PoC（Proof of Concept）が実運用に耐えるか判定するための測定基準を定義する。4つの検証軸で定量・定性の合格基準を設ける。

## 2. 検証軸

### 2.1 承認レスポンスタイム

権限確認メッセージが Slack に投稿されてから、承認者が操作を完了するまでの体感時間。

| 指標 | 測定方法 | 合格基準 |
|------|---------|---------|
| メッセージ表示遅延 | `sb serve` ログの `post_message` 完了時刻と Slack メッセージ表示時刻の差 | 3秒以内 |
| 通知到達時間 | 権限要求発生からモバイルプッシュ通知の着信まで | 5秒以内（中央値） |
| 承認操作時間 | 通知確認から Allow/Deny ボタン押下まで（モバイル） | 5秒以内（中央値） |
| E2E レスポンスタイム | 権限要求発生から Agent への応答反映まで | 15秒以内（中央値） |

### 2.2 割り込み有効性

スレッド返信による割り込み指示が Agent の動作に反映されるかの検証。

| 指標 | 測定方法 | 合格基準 |
|------|---------|---------|
| 割り込み受理率 | 割り込み指示送信数に対する Agent 動作変更確認数の割合 | 80%以上 |
| 割り込み反映遅延 | スレッド返信投稿から Agent が新しい指示に基づく動作を開始するまでの時間 | 30秒以内 |
| 割り込みACK表示 | 割り込み確認メッセージ（`追加指示を送信しました`）の表示 | 100%表示 |

### 2.3 情報十分性

Slack メッセージに表示される情報が、承認判断に十分かの検証。

| 指標 | 測定方法 | 合格基準 |
|------|---------|---------|
| ツール名の可視性 | 権限確認メッセージにツール名が明示されているか | 100% |
| リスクレベルの可視性 | 権限確認メッセージにリスクバッジが表示されているか | 100% |
| コマンド内容の可視性 | 実行コマンド/ファイルパスが確認可能か | 100%（マスキング対象を除く） |
| 承認者判断の自信度 | 表示情報のみで Allow/Deny を判断できたか（主観評価） | 「十分」または「概ね十分」が80%以上 |
| プッシュ通知の情報量 | プッシュ通知テキストのみでどのセッションの何の要求かが分かるか | 判別可能 |

### 2.4 連続稼働時間

デーモンプロセスの安定性を測定。

| 指標 | 測定方法 | 合格基準 |
|------|---------|---------|
| 連続稼働時間 | `sb serve` の無停止稼働時間 | 4時間以上（PoC段階） |
| セッション成功率 | 連続稼働中のセッション完了率（completed / total） | 80%以上 |
| メモリリーク | 稼働開始時と4時間後のプロセスメモリ使用量の差 | 100MB未満の増加 |
| Socket Mode 接続維持 | 4時間中の Socket Mode 切断回数 | 記録のみ（Phase 2 改善前の baseline） |

## 3. 判定基準

### Go 条件

以下の**全て**を満たすこと:

- 2.1〜2.3 の全指標が合格基準を達成
- 2.4 連続稼働時間が4時間以上
- 基本フロー（`sb serve` → `/claude` → 承認 → 完了）が10回中8回以上成功

### No-Go 条件

以下の**いずれか**に該当する場合:

- 基本フロー（P1-003）が1回も動作しない
- 権限確認メッセージが Slack に投稿されない
- Allow ボタン押下後に Agent に応答が伝わらない

### 条件付き Go

- 基本フローの成功率が80%未満だが50%以上の場合、バグ修正を Phase 2 前に挿入して再評価
- 特定のブロックタイプ（ThinkingBlock 等）の処理に問題がある場合、Phase 3 のスコープ調整で対応

```markdown
- 所要時間: Xs
- エラー内容: (あれば)
- 備考:
```
