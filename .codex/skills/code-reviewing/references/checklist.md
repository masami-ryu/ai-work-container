# 自己検証チェックリスト

レビュー出力前に必ず確認（目標: 全項目クリア）

## 早見表（レビュー種別 → 実行対象）

| 種別 | 実行対象 |
|------|----------|
| PR / git差分 | 共通チェック（1〜6） + 「PR / git差分レビュー固有」 |
| Markdownメタレビュー | 共通チェック（1〜6） + 「Markdownメタレビュー固有」 |
| プランレビュー | 共通チェック（1〜6） + 「プランレビュー固有」 |

## 共通チェック（全レビュー種別）

### 1. 完全性チェック
- [ ] レビューの全観点がカバーされているか
- [ ] 5つのPhaseすべてが完了しているか

### 2. 具体性チェック
- [ ] 指摘内容が**具体的で実行可能**か（曖昧な表現を避ける）
- [ ] 改善提案に**コード例**が含まれているか（必須ではないが推奨）

### 3. 建設性チェック
- [ ] 各指摘に**改善提案**が含まれているか

### 4. エビデンスチェック（最重要）
- [ ] エビデンス付与率が基準を満たしているか（基準: [feedback-format.md](feedback-format.md) の「エビデンス付与率」参照）
- [ ] エビデンスが**実際に参照可能**か（URLが有効か）

### 5. 優先度チェック
- [ ] 重要度（高/中/低）が**明確に示されている**か
- [ ] セキュリティ問題は**重要度:高**として明記されているか
- [ ] 軽微な問題は**重要度:低**として適切に分類されているか

### 6. フォーマットチェック
- [ ] Markdown形式が正しいか
- [ ] コードブロックに言語指定があるか
- [ ] 絵文字（🔴🟡🟢✅）が適切に使用されているか

## 種別固有チェック

### PR / git差分レビュー固有

#### 1. ファイル・行番号チェック
- [ ] すべての指摘に**ファイル名と行番号**が明記されているか（形式: `file.js:42`）
- [ ] 変更されたすべての重要ファイルがレビューされているか

#### 2. 影響範囲チェック
- [ ] 変更による影響範囲が分析されているか
- [ ] 依存関係のあるファイルが確認されているか

### Markdownメタレビュー固有

#### 1. 観点網羅性チェック
- [ ] 元のレビューが全観点（品質/セキュリティ/パフォーマンス/テスト/設計）をカバーしているか評価されているか

#### 2. 指摘の具体性チェック
- [ ] 元のレビューの指摘にファイル名:行番号が含まれているか確認されているか
- [ ] 元のレビューのコード例の有無が評価されているか

#### 3. エビデンス付与率チェック
- [ ] 元のレビューのエビデンス付与率が計算されているか（基準: [feedback-format.md](feedback-format.md) 参照）

#### 4. 重複/矛盾チェック
- [ ] 元のレビューに重複する指摘がないか確認されているか
- [ ] 元のレビューに矛盾する指摘がないか確認されているか

#### 5. 建設性チェック
- [ ] 元のレビューが批判だけでなく改善提案を含んでいるか評価されているか

### プランレビュー固有

#### 1. 前提検証チェック
- [ ] プランが参照する対象ファイルが実在するか検証されているか
- [ ] 既存実装・アーキテクチャとの整合性が確認されているか

#### 2. タスク設計チェック
- [ ] 各タスクの完了条件が**測定可能**か評価されているか
- [ ] タスク間の依存順序が正しいか確認されているか
- [ ] タスクの粒度が実装可能なサイズか評価されているか

#### 3. リスク・影響範囲チェック
- [ ] 破壊的変更の有無が確認されているか（該当する場合）
- [ ] 主要リスクへの対策が評価されているか

#### 4. 実装着手可否の判断
- [ ] プランの品質に基づき、実装着手可否が**明記**されているか
- [ ] ステータス推奨（→ Approved / → Draft（要修正））が**明記**されているか

#### 5. テンプレート準拠チェック
- [ ] 評価サマリーテーブル（5観点: 完全性/実現可能性/タスク設計/測定可能性/リスク対応）が含まれているか
- [ ] 改善提案が重要度（🔴🟡🟢）で分類されているか
- [ ] 指摘箇所がID（TASK-XXX, REQ-XXX等）またはセクション番号で特定されているか
