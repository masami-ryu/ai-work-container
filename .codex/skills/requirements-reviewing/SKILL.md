# Requirements Reviewing

要件定義書をレビューし、矛盾・未定義・検証不能な要件を優先度付きで抽出する。

## 入力

- 対象ファイル: 要件定義書（単一ファイルまたは複数ファイル構成）
  - 対象ファイルが存在しない場合はユーザーにパスの確認を求める
  - 複数ファイル構成の場合: INDEX → 概要 → 各機能 → 非機能の順で読み、ファイル間参照の整合も検証対象とする
- 目的: 全体レビュー / 追記分レビュー（ユーザーが明示的に「追記分」「差分」等を指定した場合のみ追記分レビュー。未指定時は全体レビュー）
- 既存レビュー: `ai/reviews/` 内の最新レビュー結果1件のみ参照する（コンテキスト節約のため。ファイル名のタイムスタンプで最新を判定）

## レビュープロセス

### Step 1: 文書構造の把握と既存レビュー確認

1. 見出し一覧を抽出して章構成を把握する
2. 複数ファイル構成の場合、ファイル間の参照関係（相互リンク・用語の定義元）を特定する
3. 用語（ロール名、データ名、計算用語）の定義位置を特定する
4. `ai/reviews/` に既存レビューがあれば**最新の1件のみ**読み、過去の指摘が解決されたか確認する。解決済みの指摘は再提出しない

### Step 2: 章横断の整合チェック

以下の観点で**章・ファイルをまたぐ矛盾と解釈分岐**を検出する（個別項目の網羅確認は Step 3 の checklist で行う）。

- 同一概念（ロール、データ、計算ルール）が複数箇所で異なる定義になっていないか
  - **原則と例外の追跡**: ある箇所で「不可」「禁止」等の原則が記載されている場合、他のファイル・章で例外が定義されていないかを確認する。例外が明示されている場合は「矛盾」ではなく「例外あり」として扱い、例外側の統制ルール（承認・ログ等）の妥当性を評価する
- 未決事項と解決済み項目の間に重複・逆戻りがないか
- **未決事項として追跡済みの項目を指摘しない**: 「基本設計で定義する」等として未決事項セクションで明示的に先送りされた項目は、未定義であること自体を指摘しない。ただし、未決事項の記載内容と本文の記述に矛盾がある場合は指摘する
- 複数ファイル構成の場合、ファイル間の相互参照が正確か（リンク先の節が実在し、参照先の記述と矛盾しないか）

### Step 3: 完全性と検証可能性の評価

[references/checklist.md](references/checklist.md) の各項目を要件定義書に照合し、未充足の項目を指摘として報告する。

**追記分レビュー時**（ユーザーが「追記分」「差分」等を指定した場合のみ）は、以下の手順で差分に集中する。

1. 以下の優先順で差分を特定し、変更・追加された節を列挙する
   1. ユーザーが指定した範囲（コミット範囲やファイル範囲）
   2. 前回レビューファイルにコミットハッシュが記載されている場合、そのハッシュとの `git diff`
   3. `git log` で対象ファイルの最終変更コミットを特定し、その直前コミットとの diff
2. 最新の既存レビューの指摘と重複する論点は再提出しない
3. 追記部分が既存の章と矛盾していないか、Step 2 の観点で横断チェックする
4. 過去の指摘が今回の追記で解決された場合、「解決確認」として記録する

### Step 4: 指摘の優先度分類

以下の判定基準で分類する。

- **HIGH**: 金銭計算に影響する / 実装不能になる / 法令違反リスクがある / 監査で指摘される
- **MEDIUM**: 実装解釈が分岐し結果差異の恐れがある / 運用開始後に手戻りが発生する
- **LOW**: 表現の曖昧さ、補足不足（運用で吸収可能）/ UX改善の提案

**意図的な逸脱の重要度判定**: 法令要件等からの逸脱であっても、要件定義書中に以下の条件を**すべて**満たす記述がある場合は、HIGHではなくLOW（既存の緩和策の補足提案）として扱う。

1. 逸脱が意図的であることが明記されている（「〜は行わない」「〜を省略する」等）
2. 逸脱の理由が記載されている（運用実態、規模等）
3. リスク緩和策が記載されている（専門家確認、リスク受容の文書化、手動例外対応、監査証跡等）

### Step 5: 出力作成と保存

[references/output-template.md](references/output-template.md) のテンプレートに従って出力する。

- 保存先: `ai/reviews/`
- 命名規則: `YYMMDD_HHmm_[概要]_レビュー.md`（`HHmm` は JST/UTC+9）
- 出力品質の自己検証:
  - すべての指摘に該当箇所を記載したか（単一ファイル: `L行番号`、複数ファイル: `ファイル名 L行番号`）
  - HIGHには具体的な改善提案（対策案の選択肢または推奨案）を付与したか
  - 推奨アクションが実行可能な粒度で整理されているか
  - 未決事項への追記提案を含めたか（新たに発見された未定義事項がある場合）
  - 最新の既存レビューの指摘と重複していないか

## 運用ルール

- 既存仕様を変更する提案は、影響範囲（どの章・ファイルに波及するか）を明記する
