# Development Cycle

現在の成果物を正として次タスクを選定し、採用後の実装から品質ゲートとコミットまでを管理する。ユーザーによるタスク選定の承認を残し、それ以降の定型工程を可能な範囲で一括実行する。

## モードを選択する

ユーザーの依頼と直前の会話から、次のどちらかを選択する。

- **提案モード**: 次にやるべきことの提案を求められた場合
- **実行モード**: 直前の提案を採用し、着手または完了まで進めるよう求められた場合

採用対象が会話から一意に決まらない場合は実装せず、対象タスクを確認する。実装中にユーザーが方向を変更した場合は最新の指示を優先する。

レビュー重要度は`code-reviewing`の出力に合わせて「高」「中」「低」を使用する。外部のレビューがCritical／High／Medium／Lowを使う場合は、CriticalとHighを「高」、Mediumを「中」、Lowを「低」として扱う。

## 提案モード

1. 作業ルートと配下の `AGENTS.md` を読み、リポジトリ境界と作業規約を確認する。
2. 各リポジトリの `git status`、直近コミット、現在のコード、テスト、要件・設計文書を確認する。
3. `ai/plans` の古いプランを実行基準にしない。現在のコード、現在の文書、テスト結果、Git履歴を正とする。
4. このターンで実行していない検証を「現在成功している」と表現しない。過去の検証記録を参照する場合は、実行時点と情報源を明示する。
5. 提案のためだけに高コストな全テストを実行しない。必要性と影響範囲の判断に必要な調査へ限定する。
6. 最新の関連レビューと作業ツリーを確認し、指摘や差分が現在も未解決かを現行成果物で再検証する。
7. スコープ内の妥当な未解決指摘、もしくは前回タスクの未完了差分がある場合は、重要度にかかわらず新規タスクより先にその解消を提案する。
8. 未実装、仕様上の依存関係、リスク、変更規模を比較し、次に行う小さな1タスクを選ぶ。
9. 次の項目を簡潔に提示し、コードや文書を編集せず終了する。
   - 提案タスク
   - 選定理由
   - 対象範囲と対象リポジトリ
   - 完了条件
   - 想定する検証
   - 先に判断が必要な事項

ユーザーがプラン作成を明示していない限り、`ai/plans` にプランを作成しない。

## 実行モード

### 1. 作業範囲を固定する

1. 採用された提案、完了条件、対象リポジトリを会話から復元する。
2. 各対象リポジトリの作業前ベースラインとして、`git status`、ステージ済み差分、未ステージ差分、未追跡パスを記録する。
3. 既存変更または未追跡ファイルと同じファイルを編集する場合は、作業前の差分または内容も保持して今回の変更と区別する。安全に分離できない場合だけユーザーへ確認する。
4. コミット許可を判定する。
   - 「コミットして」「コミットまで進めて」などの明示がある場合だけコミットする。
   - 「着手して」だけの場合は、実装、検証、レビュー修正まで進めてコミット前で停止する。

### 2. 実装する

1. 既存の設計、責務分割、命名、テストパターンに合わせる。
2. 採用された1タスクに差分を限定し、無関係なリファクタリングを行わない。
3. 振る舞いを変更する場合は、変更リスクに応じたテストを追加または更新する。
4. 編集中は短い進捗を共有し、長時間無言で作業しない。

### 3. 検証する

1. 各リポジトリの設定ファイルと既存スクリプトから正式な検証コマンドを特定する。
2. Node.js系の実行には `pnpm` を使う。
3. 変更箇所に近いテストを先に実行し、その後に標準のフォーマット、Lint、型検査、テストを実行する。
4. DBや外部サービスを変更した場合は、利用可能な検証環境で必要な統合テストも実行する。
5. 必須検証を実行できない場合は理由と残存リスクを記録する。成功を推測しない。

### 4. セルフレビューする

1. 対象リポジトリごとに、作業前ベースラインと現在状態の差分を取得して個別にレビューする。ワークスペース直下のGit差分だけで代用しない。
2. 未追跡の新規ファイルは通常のGit差分に含まれないため、`git status`から特定し、ファイル全文を追加差分としてレビューする。
3. 複数リポジトリを変更した場合は、個別レビューに加えてAPI、データ定義、要件・設計文書の整合性を横断確認する。
4. 利用可能な場合は `code-reviewing` スキルの5段階プロセスと評価基準を使う。
5. 正しさ、要件整合性、責務境界、セキュリティ、競合制御、エラー処理、テスト不足、運用影響を確認する。
6. 指摘には重要度、根拠となるファイルと行、発生条件、推奨対応を含める。
7. `AGENTS.md` に従い、レビュー結果をワークスペースルートの `ai/reviews` に保存する。同じ実行サイクルの再レビュー結果は、最初のレビューファイルへ追記して履歴をまとめる。

### 5. 指摘へ対応する

1. 各指摘をコードと要件に照らして再確認し、妥当な指摘だけを修正する。
2. スコープ内の妥当な指摘は重要度にかかわらず対応する。
3. スコープ外の改善は今回の変更へ混ぜず、残存事項として報告する。
4. 修正後に関連するフォーマット、型検査、テストを再実行する。

### 6. 再レビューを制御する

- 重要度「高」の指摘を修正した場合は、差分全体を再レビューする。
- 指摘の重要度にかかわらず、共通インターフェース、認証・認可、DBスキーマ、マイグレーション、トランザクション、競合制御、公開APIなど影響範囲が広い修正をした場合は、差分全体を再レビューする。
- 重要度「中」または「低」だけを修正し、修正の影響が局所的な場合は、修正箇所と影響範囲を重点的に再確認する。
- 重要度「高」が新たに見つかった場合は、修正、検証、再レビューを繰り返す。
- フル再レビューは最大3回とする。3回目でも重要度「高」が残る場合はコミットせず、未解決事項を報告する。
- スコープ内の妥当な指摘がすべて対応済みで、重要度「高」の未解決指摘がなく、必須検証が通った状態をコミット可能条件とする。

### 7. コミットする

コミット許可があり、コミット可能条件を満たす場合だけ実行する。

1. リポジトリごとに最終のステージ済み差分、未ステージ差分、`git status`を確認する。未追跡の新規ファイルは全文を確認する。
2. 今回変更したパスだけを明示してステージする。`git add .` を使わない。
3. 作業前から存在した変更、他リポジトリの変更、`ai/reviews`、`ai/plans` を混入させない。
4. リポジトリの慣例に沿い、今回の目的を表すコミットメッセージを作る。
5. コミットフックが失敗した場合は原因を修正し、必要な検証とレビューをやり直す。
6. リポジトリが複数ある場合は、それぞれ独立してコミットする。
7. 明示がない限り、既存コミットをamendしない。変更がなければ空コミットを作らない。
8. 各コミット後に `git show --stat --oneline HEAD` と `git status --short` を確認する。
9. コミット内容が今回の対象ファイルと一致し、作業前にはなかった未コミット差分が今回の作業によって残っていないことを確認してから完了とする。

## 停止条件

次の場合はコミットせず、判明した事実と必要な判断を報告する。

- 要件の曖昧さが外部仕様、データ整合性、セキュリティへ影響する
- 既存変更と安全に分離できない
- 必須検証が失敗して解消できない
- スコープ内の妥当な指摘に対応できない
- 重要度「高」が再レビュー上限後も残る
- 秘密情報、破壊的操作、本番環境への変更が必要になる

## 完了報告

次を簡潔に報告する。

- 実装した内容
- 実行した検証と結果
- セルフレビューと指摘対応の結果
- リポジトリごとのコミットハッシュ（コミットした場合）
- 未実施項目または残存リスク

すべて完了した場合は、最後にクライアント側で `/compact` を実行できることを案内する。スキル自身からSlash Commandを実行しない。
